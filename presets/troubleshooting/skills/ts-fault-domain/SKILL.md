# Fault domain（故障域分层）

**第一步永远是判定故障域**——它决定证据从哪来、排查路径怎么走。误判故障域是最常见的时间浪费。

## 0. 判定流程

```
现象描述 → 问三个问题：
  1. 故障对象在哪里？ 本机进程/服务/资源 | 远程主机/服务/云资源 | 跨环境调用链
  2. 我有这个对象的直接访问吗？ 本地命令 | SSH/API/控制台 | 只有日志/指标
  3. 最近有无环境/配置变化？ 部署 | 配置变更 | 网络变更 | 无
→ 落入下表对应域（可多域：先主域后次域）
```

## 1. 本机故障（local）

**特征**：故障对象在本机（进程/端口/服务/文件/资源占用）。

| 证据源 | 路径 | 典型动作 |
|---|---|---|
| 进程/服务 | `ps`/`systemctl status`/`ss -ltnp` | 存活？重启历史？ |
| 资源 | `top`/`df`/`free`/`dmesg` | CPU/内存/磁盘/OOM？ |
| 日志 | 系统日志/应用日志文件 | 尾部 + 时间窗 grep 错误 |
| 配置 | 进程的配置文件/env | 与基线 diff |
| 变更 | `journalctl`/包管理历史/shell 历史 | 最近装了什么、改了什么 |

**本机经验库**：本机专属教训进 `sop/本机经验/`（带上机器特征）；通用结论进 `sop/通用故障模式/`。

## 2. 远程故障（remote）

**特征**：故障对象在远程（目标主机/服务/云资源/依赖链下游），经连接层排查。

| 证据源 | 路径 | 典型动作 |
|---|---|---|
| 连通性 | `ssh`/`ping`/`curl -v`/`nc`/`traceroute` | 通不通、超时在哪一跳 |
| 远程服务 | SSH 后 `systemctl`/日志/端口 | 同本机流程但**带远程上下文** |
| API/云控制台 | 平台 API、云控制台指标 | 实例状态、配额、限流 |
| 依赖链 | 上游/下游健康、超时配置 | 是本方还是对端问题 |
| 凭据/权限 | 密钥/令牌过期、ACL | 401/403/权限不足 |

**边界纪律**：先区分「我方问题 vs 对端问题」——用最小探测（一个 curl/一条命令）把故障定位到边界一侧，再决定往哪边深挖。远程操作要先确认授权（哪些主机可以动、什么操作可执行）。

## 3. 环境差异故障（environment-aware）

**特征**：同样的代码/配置在不同环境（dev/test/prod）表现不同，或跨环境调用失败。

| 差异维度 | 检查项 |
|---|---|
| 配置差异 | env 文件/配置文件 diff（dev vs prod 的 URL/端口/超时/开关） |
| 网络隔离 | VPC/防火墙/SG/白名单是否放行、跨环境地址可达性 |
| 凭据差异 | 不同环境的密钥/证书/token 是否过期或未配置 |
| 资源差异 | 实例规格/配额/并发限制（测试没问题生产爆了 → 看配额/规格） |
| 数据差异 | 生产数据规模/分布 vs 测试（慢查询/大表） |

**环境基线**：每个环境维护一份「环境基线」文档（组件版本/配置要点/网络拓扑），故障时先对照基线找差异，而不是从头猜。

## 4. 跨域协作

- **多域故障**：先主域（现象直接指向的域）后次域；证据链要能跨域衔接（如本机日志显示连接被远端拒绝 → 转远程域）。
- **经验分层归档**：
  - `sop/通用故障模式/`：与环境、机器无关的通用结论（可复用、可移植）；
  - `sop/本机经验/`：带本机特征的教训（路径、版本、机器名）；
  - `sop/环境基线/`：各环境的组件版本/配置/拓扑快照，用于环境差异对照。
- 归档时先问：「这条结论换台机器还成立吗？」成立 → 通用；不成立 → 本机。

## 5. 反模式

- 跳过故障域判定直接查日志/指标 —— 可能查错源；
- 本机没问题却怀疑远程（或反之）—— 先用最小探测定位边界；
- 把环境差异当代码 bug —— 先对照环境基线；
- 数据源未配置/工具失败却继续推结论 —— 先如实报告限制。
